# Release v1.0.1 - Logging Must Not Abort the Caller

**Release date:** 2026-08-22
**Previous version:** 1.0.0

## Summary

A patch release for a defect that silently disabled the entire service control
surface. Six scripts run under `set -euo pipefail` and set `ORADBA_LOG_FILE`
themselves, bypassing the writability fallback in `init_logging`. A missing
`/var/log/oracle` therefore did not produce a warning - it killed the script at
its first log call. On a systemd-managed host that meant the unit failed and the
database never started, with a message that pointed at logging rather than at
Oracle.

On top of that, `oradba_services_root.sh` called an undefined `log_message` and
exited 127 in line 189, before `check_root` was ever reached. Its entire body
had never been executed.

Found by a reboot test of a lab host running Oracle 19c under
`oradba-services.service`.

## Changes

### Fixed

- `src/lib/oradba_common.sh` `oradba_log`: file logging can no longer abort the
  calling script. A new `_oradba_log_to_file` helper creates the target
  directory on demand and drops the line silently when that is impossible,
  leaving the stderr copy as the record. Affected callers:
  `oradba_services.sh`, `oradba_services_root.sh`, `oradba_dbctl.sh`,
  `oradba_lsnrctl.sh`, `oradba_dsctl.sh` and `oradba_rman.sh`.

- `src/bin/oradba_services_root.sh`: 13 calls to the undefined `log_message`
  renamed to `oradba_log`, which `oradba_common.sh` provides with the same
  `<LEVEL> <message>` signature. `log_message` only ever existed in
  `src/templates/init.d/oradba`, which defines it itself and is unaffected.

- `src/doc/api/`: API reference regenerated from the function headers. Adds
  `_oradba_log_to_file` and clears drift in `common.md`, `function-index.md`,
  `index.md`, `plugins.md` and `scripts.md` accumulated since the last run.

### Added

- `src/doc/troubleshooting.md`: section "Issue: systemd service does not start
  the database", covering both failure signatures with check, fix and a
  verification step that exercises the root wrapper independently of systemd.

- `src/doc/operations.md`: `${ORADBA_LOG}` defaults to `/var/log/oracle`, has to
  exist and be owned by the Oracle user at install time, and the write path
  behaviour from 1.0.1 on.

- `doc/development.md`: section "Logging Invariants". Logging must never abort
  the caller, file writes go through `_oradba_log_to_file` rather than a direct
  append, and `log_message` is not part of the library.

## Upgrade Notes

No configuration change is required. Creating the log directory explicitly is
still recommended, so the service logs are actually written:

```bash
sudo mkdir -p /var/log/oracle
sudo chown oracle:oinstall /var/log/oracle
sudo chmod 755 /var/log/oracle
```

Hosts that manage Oracle through systemd or init.d should upgrade. Before 1.0.1
`oradba_services_root.sh` could not complete a single action.

## Verification

- `shellcheck` and `shfmt -i 4 -bn -ci -sr` clean on the changed scripts
- 375 Bats tests pass, 0 failures
- `oradba_services_root.sh status` as a non-root user now reports the root
  check instead of exiting 127
