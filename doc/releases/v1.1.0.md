# Release v1.1.0 - Closing the Gate That Let Four Releases Through

**Release date:** 2026-08-28
**Previous version:** 1.0.4

## Summary

The boot-path cascade of v1.0.1 to v1.0.4 was never the real problem. The real
problem was that a red test suite did not stop a single one of those releases.
This release fixes that, and it turns out the mechanism was worse than assumed.

`make test-full` - the exact command the release workflow uses as its gate -
called bats with `--output tests/results`. That directory is neither tracked in
git nor listed in `.gitignore`, so it does not exist in any fresh checkout. bats
aborted with its help text, the `grep -c '^not ok'` on the missing report
failed, `$failures` stayed empty, `[ "" -gt 0 ]` errored out (exit 2, which the
`if` reads as false) and the recipe fell through to its success message:

```text
All tests passed (failures: 0)
```

Exit code 0. The gate did not fail to evaluate a red suite - it never ran a
single test. Seven failing tests reached three tagged releases through that hole.

A second, independent hole sat in CI. The `tests` path filter covered
`src/bin/**` and `src/lib/**` but not `src/etc/**`, and the `lint` job is gated
on `scripts || tests`. v1.0.4 changed only `src/etc/`, `CHANGELOG.md`, `VERSION`
and `doc/releases/` - so the release that fixed the config defect passed through
CI without one test and without one linter.

Both are closed, and the regression test that would have found the entire
cascade in one run now exists.

## The boot-path test

`tests/test_boot_path.bats` models what `systemd` actually hands to oradba
through `su - oracle -c`: `HOME`, `PATH`, `USER`, `LOGNAME` and `SHELL` set,
everything Oracle-related unset.

The review brief proposed doing this in an Oracle container. That turned out to
be unnecessary. Every defect in the cascade is a `set -u` abort that fires while
sourcing a file or parsing arguments - long before any Oracle contact. The test
therefore needs no Oracle, no container and no fixtures, and runs in the normal
suite in seconds. It is red against v1.0.0 (6 of 11 tests fail) and green after
this release.

Writing it immediately found five more instances of the same defect class that
were still live in v1.0.4:

- `oradba_standard.conf:71` expanded a bare `$ORACLE_HOME` **inside a default
  value**: `${RLWRAP_OPTS:--i -c -f $ORACLE_HOME/bin/sqlplus}`. With
  `RLWRAP_OPTS` unset, bash expands the default and aborts.
- Four guards tested for the existence of the *file* `oradba_common.sh` while
  calling functions defined in other libraries. Interactively `oraenv.sh` had
  already sourced everything, so the functions existed and the wrong guard never
  showed itself.
- `oradba_standard.conf` never sourced its own documented prerequisite, so the
  first of its 77 `safe_alias` calls aborted the config with
  `safe_alias: command not found`.
- `generate_sid_lists` returns non-zero for the legitimate case "no oratab
  entries"; under `set -e` that advisory return code killed the whole config.
- The SID-derived admin and diagnostic block expanded `${ORACLE_SID}` bare.

The pattern behind all of them is the one the brief already noted about
`oraenv.sh:1369`: the correct idiom was known and applied inconsistently. Line
444 of `oradba_standard.conf` guards `${ORACLE_SID:-}` correctly, fourteen lines
above one that did not.

## M1 - profile wiring

`--profile-user USER` wires that user's profile and hands the installed tree to
them. `${HOME}` is correct only when the installer runs as the Oracle user,
which is the intended way; under `sudo` or Ansible `become: true` it is `/root`,
and the Oracle user's profile was never touched. The home directory is resolved
via `getent passwd`, falling back to tilde expansion on hosts without `getent`.

When run as root with `--profile-user`, the prefix and the log directory are
chowned to that user and group. That also removes the root-owned
`/var/log/oracle` the Oracle user could not write into. If ownership cannot be
set, that is reported together with the corrective command - it is never skipped
silently, because a silent skip looks exactly like a successful install.

## M5 - `--force` and justification

Decision: **fail with a clear message**, do not imply `--force`.

With a non-terminal stdin, `read` consumes EOF, gets an empty justification and
cancels with "No justification provided" - which reads like a policy decision
rather than a missing flag. All three scripts carrying the pattern
(`oradba_dbctl.sh`, `oradba_dsctl.sh`, `oradba_lsnrctl.sh`) now fail naming
`--force`.

Implying `--force` was rejected deliberately: it would silently widen an
all-databases operation to every cron job, pipe and CI step. The `systemd` path
is unaffected - `oradba_services_root.sh` already passes `--force`.

## The seven test failures

All triaged. Only the first was a product defect, and it led to a real one:

| Test | Cause |
| --- | --- |
| `installer has preserve_configs function` | Function renamed to `preserve_runtime_files`. Investigating it found that `--update` silently discarded user `sid.<SID>.conf` files. |
| `generate_sid_aliases creates rlwrap aliases ...` | Queried the alias via `run bash -c "alias sq"`. Aliases are not exported, so a new shell can never see them - unpassable regardless of the product. |
| `sqh alias connects with sysdba ...` | Same cause. |
| `show_status calls setup_connector_environment` | `grep -A10` from the function header; a three-line comment pushed the call to line 11. |
| `oradba_version.sh --info shows comprehensive information` | Asserted the heading `Installation Details:`, shortened to `Installation:` in 5cd54df without updating the test. |
| `datasafe_plugin.sh supports ORADBA_CACHED_PS ...` | Asserted a mechanism 443fc0c removed as broken in favour of a port-based check. |
| `datasafe_plugin.sh falls back to ps -ef ...` | Same cause. |

Six of seven were stale or structurally broken tests, not regressions. That is
its own finding: a suite nobody could act on because the gate never reported it.

## Upgrade notes

- No action required for existing installations.
- `--update` now preserves user `sid.<SID>.conf` files. If you worked around the
  old behaviour by keeping copies elsewhere, that is no longer necessary.
- Unattended callers that relied on an all-databases operation cancelling itself
  through the justification prompt now get an explicit failure naming `--force`.
  Add `--force`, or name the databases.
- Installing as root for another user: add `--profile-user oracle`.

## Deliberately not in this release

The M6 asset question - whether oradba is the canonical home for dbca response
files, sqlnet templates, systemd units, AutoUpgrade configuration and
verification SQL - is untouched. It couples to the repo-boundary decision and
must not be settled alongside bugfixes.

## Verification

- Boot-path test red against v1.0.0 (6 of 11), green here.
- The gate proven on four paths: red suite fails, bats-cannot-start fails,
  missing report fails, green-with-skips passes. The old recipe was replayed
  under the fresh-checkout condition and confirmed to exit 0 with a deliberately
  failing test present.
- `make lint-shell` clean; markdownlint clean.
