# Release v1.0.4 - What 1.0.3 Was Meant to Ship

**Release date:** 2026-08-23
**Previous version:** 1.0.3

## Summary

1.0.3 described the boot-path fix correctly and did not contain all of it. Two
lines in `src/etc/oradba_core.conf` - the ones the whole cascade actually hangs
on - were lost between the edit and the commit. The release therefore reported
success while an updated host still aborted while sourcing its own
configuration.

A second, independent gap surfaced with it: `src/etc/` had only ever been
processed with a narrow pattern covering `-z` and `-n` tests, while `src/lib/`
and `src/bin/` got a broader one covering any braced uppercase variable inside
`[[ ]]`. Comparisons like `[[ "${ORADBA_RLWRAP_FILTER}" == "true" ]]` slipped
through.

## Changes

### Fixed

- `src/etc/oradba_core.conf:30,31` - `${ORADBA_LOCAL_BASE}` and
  `${ORACLE_BASE}`. This is the actual blocker: every `bin/` script sources
  this file, and under `set -euo pipefail` an unguarded reference kills the
  caller before it reaches any Oracle command.
- `src/etc/` - 15 further `[[ ]]` tests guarded, bringing all three directories
  to zero remaining occurrences.

## Verification

Verified against the committed tag content, not against the output of the
patching step - which is how the 1.0.3 gap went unnoticed:

```text
src/etc: 0 remaining
src/lib: 0 remaining
src/bin: 0 remaining
```

1720 Bats tests with the same 7 pre-existing failures as `v1.0.1`.

## Known Limitations

Unchanged from 1.0.3: the same seven test failures remain open, neither CI nor
the release workflow blocks on them, and there is still no regression test that
exercises the boot path without a loaded profile. A container that runs
`oradba_services.sh start --force` with an empty environment would have caught
every layer of this cascade in one run - including the fact that 1.0.3 did not
fix what it claimed.
