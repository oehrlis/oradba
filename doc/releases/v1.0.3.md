# Release v1.0.3 - The Boot Path, All Six Layers

**Release date:** 2026-08-22
**Previous version:** 1.0.2

## Summary

The third and final release in a cascade that started with a single reboot test
of an Oracle 19c lab host. Six defects, one defect class, each only visible once
the one before it had been removed.

| Layer | Location | Defect | Fixed in |
| --- | --- | --- | --- |
| 1 | `oradba_services_root.sh:189` | undefined `log_message`, exit 127 | 1.0.1 |
| 2 | `oradba_log` | a log write aborted its caller | 1.0.1 |
| 3 | `oradba_lsnrctl.sh:161` | bare `${TNS_ADMIN}`, listener never started | 1.0.2 |
| 4 | `oradba_core.conf:30` | bare `${ORADBA_LOCAL_BASE}` | 1.0.3 |
| 5 | `oradba_env_parser.sh:19` | bare include guard | 1.0.3 |
| 6 | `oraenv.sh:1368` | bare `${ORACLE_HOME}` | 1.0.3 |

The design was never the problem. `oradba_dbctl.sh` sources `oraenv.sh` itself
and derives `ORACLE_HOME` from oratab, so the tools do not depend on a login
profile. What did not work was the loading path: under `set -euo pipefail` the
scripts died while reading their own configuration.

Why it went unnoticed for so long is worth stating plainly. An interactive shell
has sourced the oradba profile, so `ORACLE_HOME`, `ORACLE_SID` and `TNS_ADMIN`
are all set and `set -u` never fires. systemd starts through `su - oracle` with
no profile at all. **Verifying a service script from an interactive session
proves nothing about boot.**

## Changes

### Fixed

- 291 `[[ ]]` tests on braced uppercase variables across `src/etc/`,
  `src/lib/` and `src/bin/` now use `${VAR:-}`.

  This completes what 1.0.2 started. The 1.0.2 release notes recorded the
  remaining cases as "a refactor, not a hotfix" and deferred them. That
  assessment was wrong: they were the blocker, and the boot path failed three
  more times because of it.

  `${VAR:-}` is behaviour-preserving for `-z`, `-n` and string comparison - an
  unset variable and an empty one were always meant to be treated alike. Adding
  the guard to a variable the script sets itself is a harmless no-op. Applying
  it uniformly is cheaper and safer than deciding case by case, which is how
  1.0.2 left three layers behind.

### Added

- `doc/development.md`: the `set -u` section now covers every sourced layer -
  config files, libraries and module include guards - not just the entry script.

## Upgrade Notes

Required for any host that starts Oracle through systemd or init.d. Before
1.0.3, `oradba_services.sh start --force` could not complete a single unattended
start on a host without a loaded oradba profile.

```bash
sudo mkdir -p /var/log/oracle
sudo chown oracle:oinstall /var/log/oracle
sudo chmod 755 /var/log/oracle
```

## Verification

- 1720 Bats tests, 7 failures - byte-identical to the `v1.0.1` baseline. No
  regression from a 291-line mechanical change.
- No new ShellCheck findings; `shfmt -i 4 -bn -ci -sr` clean.
- End to end on Oracle Linux 8 with Oracle 19c under systemd: listener and
  database start unattended, `Database CPUDB started successfully`.

## Known Limitations

The same seven pre-existing test failures as in 1.0.1 and 1.0.2 remain open:

```text
not ok  installer has preserve_configs function
not ok  generate_sid_aliases creates rlwrap aliases when rlwrap is available
not ok  sqh alias connects with sysdba when rlwrap available
not ok  show_status calls setup_connector_environment
not ok  oradba_version.sh --info shows comprehensive information
not ok  datasafe_plugin.sh supports ORADBA_CACHED_PS environment variable
not ok  datasafe_plugin.sh falls back to ps -ef when no cache
```

Neither CI nor the release workflow blocks on a red suite. That gate is what
allowed seven failures into three tagged releases, and it belongs in a
follow-up together with the failures themselves.

There is no regression test for the boot path. Everything above was caught by
rebooting a real host by hand. A container-based test that starts the service
without a profile would have caught all six layers in minutes.
